Architecture review — Audit Logging

platform-admin-v2 · FastAPI / SQLModel · 2 Sep 2026 · scope: the Audit Logging module (BRD §2.1) and its 25 call sites

module seam leakage deep module

Coupling verdict

The module's infrastructure edges are loosely coupled — ambient actor/request context flows through a ContextVar seam (mirrors django-auditlog's middleware pattern), the repository has a second adapter in tests (FakeAuditRepository), and redaction sits at exactly one point before persistence. The business-facing interface is the problem: record() exposes 12 loose kwargs, 25 call sites hand-assemble events, auth.py repeats one failure/success template 5×, and the list filters exist as four copies of the same 8-param list. Interface nearly as wide as the implementation — shallow where it should be deep.

How this compares to industry practice

Already aligned

  • OWASP ASVS security-event catalogue: logins, denials, exports, lockouts — all recorded
  • Secret redaction before persistence (ASVS: never log credentials)
  • Middleware-fed actor context — the django-auditlog / AuditKit pattern
  • Four-field core shape: who (actor), what (action), on-what (resource), outcome (details/payload/response)

Gaps vs. the standards

  • No tamper evidence — ASVS 7.3.3 wants logs protected from modification; industry default is a hash chain
  • No first-class reason/why field — the BRD's "mandatory change reasons" have no audit-event slot
  • Best-effort write after the change — the BRD's "durable Pending Audit Intent before every change" is the transactional-outbox pattern, not implemented

Sources: OWASP ASVS v5 §16 / v4 §7.3.3 & Logging Cheat Sheet · django-auditlog (jazzband) internals · pydantic, "PostgreSQL Triggers vs Async Audit Logs" (app-level explicit recording beats triggers for ORM stacks) · AWS Prescriptive Guidance, transactional outbox · 137Foundry evidence-log pattern (query log + hash-chained evidence log).

Problem. record() is shallow — 12 loose kwargs where most callers pass 4–6, and hidden invariants (pre-auth endpoints pass actor explicitly because the ambient seam is empty; explicit beats ambient). The failure/success audit policy lives in auth.py, repeated 5×.

Solution. An AuditEvent value with 3 required fields (action, resource_type, resource_id) and optional details/payload — plus a reserved reason slot for the BRD's mandatory change reasons. Ambient absorption stays inside the module; the auth template becomes one record_failure(exc, …) / record_success(…) pair owned by the audit module.

  • locality: audit policy in one module
  • leverage: 25 call sites, one shape
  • interface: 12 kwargs → 1 event, 3 required
  • tests: 5 auth templates → 1, via the existing fake
  • deletion test passes: kwarg-juggling vanishes into the module
  • reason field: BRD change-reasons get a home

Problem. The list path is a pure forwarder — the service function passes the deletion test as a pass-through — and its 8 params are declared at four layers. Date-combining semantics (datetime.combine) live in the repository, invisible from the interface.

Solution. An AuditLogFilter DTO assembled at the API boundary, handed down unchanged; the repository reads filters from it. The layering stays — the param echo goes.

  • interface: 8 params → 1
  • locality: filter semantics in one module
  • new filter: one edit, not four
  • tests: simpler fake setup

3 · Tamper-evident chain inside the Audit Entry module

Worth exploring local-substitutable

app/models/audit_log.py · app/repositories/audit_repository.py (create_audit_log)

Before — append-only by convention only

entry n-1 · created 10:02:14
entry n · created 10:02:15 ← edited directly in DB, nothing detects it
entry n+1 · created 10:02:19
no update/delete endpoint exists — but the row isn't protected

After — hash-chained evidence

entry n-1 hash=af3c…
prev_hash + canonical(entry) → SHA-256
entry n prev=af3c… hash=91be…
prev_hash + canonical(entry) → SHA-256
entry n+1 prev=91be… hash=0d7e…

computed inside create_audit_log — the module's single write path · verify endpoint/script walks the chain

Problem. "Immutable audit evidence" (BRD §1) is enforced by convention — no endpoint mutates rows, but nothing detects a direct DB edit, deletion, or reorder. ASVS 7.3.3 expects logs protected from modification.

Solution. prev_hash + entry_hash columns, computed in create_audit_log — one write path, so integrity logic concentrates there. Callers unchanged.

  • locality: integrity in the one write path
  • leverage: zero caller changes
  • testable through the existing repository seam
  • BRD "immutable evidence" becomes provable
Design decision to settle: concurrent writers racing on prev_hash — serialize (advisory lock / retry) or flag gaps at verify time.

4 · Durable Pending Audit Intent — the outbox adapter

Speculative ports & adapters

app/services/audit_service.py · new: app/models/audit_intent.py + forwarder

Before — audit after the fact, best-effort

sequenceDiagram
  participant C as caller
  participant B as business write
  participant A as audit write
  C->>B: business tx (commit)
  B-->>C: ok
  C->>A: separate tx (commit)
  Note over A: ✗ crash here = evidence lost forever
  Note over A: ✗ DB down = action un-audited, only a log line

After — intent commits with the change

sequenceDiagram
  participant C as caller
  participant T as one tx
  participant F as forwarder
  C->>T: intent row + business write (same commit)
  Note over T: durable Pending Audit Intent — BRD §1
  F->>F: promotes intents → Audit Entries
  Note over F: outcome is an explicit state, never a swallowed exception

Problem. Today's audit write is best-effort after the business change: a crash between the two commits loses evidence; a database outage yields silently un-audited actions. The BRD's control model demands the opposite: "durable Pending Audit Intent before every change… no timeout, unknown outcome or dependency failure ever produces a fabricated success."

Solution. The transactional-outbox pattern (AWS Prescriptive Guidance): an intent row written in the same request transaction as the business change; a forwarder promotes intents into Audit Entries and records failures as first-class outcomes. The seam is real — a second adapter (SIEM / evidence export) is exactly where the BRD's export-evidence story is heading.

  • evidence survives crashes and rollbacks
  • failure modes become explicit states
  • real seam: DB now, evidence export later
  • biggest change of the four — phase it
Contradicts today's best-effort simplicity — deliberately. Sequence it with the first governed module (Price / ED), where the BRD requirement actually bites.

Top recommendation

1 · Deepen the Audit Entry interface

Highest friction per change: every new endpoint pays the 12-kwarg study, auth pays it five times over, and the audit policy the BRD cares about lives in the wrong module. Purely in-process, no schema change, and it makes candidates 2–4 cheaper afterwards — the event object is the natural carrier for a reason field today and an intent row later.
